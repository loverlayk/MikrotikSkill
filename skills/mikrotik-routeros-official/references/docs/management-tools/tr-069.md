# TR-069

> Manage RouterOS devices from a TR-069 (CWMP) Auto Configuration Server: connect the router over HTTPS, allow connection requests, troubleshoot sessions, change the configuration, upgrade RouterOS, upload files and...

# TR-069

The TR-069 client implements the CPE WAN Management Protocol (CWMP), standardized by the Broadband
Forum (BBF). The router (the CPE) connects over HTTP or HTTPS to an Auto Configuration Server (ACS),
which can read and change parameters, run RouterOS scripts, upgrade RouterOS, upload the
configuration and the log, and reset the router. ISPs use it to manage customer routers; it also
works for managing network infrastructure devices.

The client is in the `tr069-client` package, which is not part of the main RouterOS package.
Install it as described in [Packages](../getting-started/installation-and-upgrade/packages). The
client is disabled by default.

## Connect the router to an ACS

This example connects a router with the default configuration to the ACS at
`https://acs.example.com:7547/`, whose address is 198.51.100.10. Before you start, upload the CA
certificate that signed the ACS certificate to the router as `acs-ca.crt` (see
[Files](../system-information-and-utilities/files) for the ways to upload a file), and
create the device credentials on the ACS.

```routeros
/certificate/import file-name=acs-ca.crt passphrase=""
/tr069-client/set acs-url=https://acs.example.com:7547/ \
    username=cpe-0001 password=Cpe-0001-secret \
    connection-request-username=acs \
    connection-request-password=Acs-request-secret enabled=yes
/ip/firewall/filter/add chain=input action=accept protocol=tcp \
    dst-port=7547 src-address=198.51.100.10 in-interface-list=WAN \
    place-before=[find comment~"not coming from LAN"] \
    comment="TR-069 connection requests from the ACS"
```

- The import deletes the file and adds the CA as a trusted certificate. With the default
  `check-certificate=yes`, the router connects only if the ACS certificate is signed by a CA in the
  store and its name matches the host in `acs-url`.
- `username` and `password` are the credentials the router uses to log in to the ACS.
- `connection-request-username` and `connection-request-password` are the credentials the ACS uses
  to ask the router to start a session (a connection request). Always set them.
- The firewall rule lets connection requests from the ACS reach the router. The client adds no
  firewall rule itself, and the default configuration drops them with all other input from the
  interfaces in the `WAN` list. The rule is placed before the default rule
  `defconf: drop all not coming from LAN`. Without the rule, the router still contacts the ACS on
  its own events and periodically, but the ACS cannot reach it in between.

Check the client:

```routeros
/tr069-client/print
```

```text
                      enabled: yes
                      acs-url: https://acs.example.com:7547/
                     username: cpe-0001
      periodic-inform-enabled: yes
     periodic-inform-interval: 1d
  connection-request-username: acs
      connection-request-port: 7547
            provisioning-code:
           client-certificate: none
            check-certificate: yes
                       status: running
           last-session-error:
                  retry-count: 0
```

An empty `last-session-error` with `retry-count: 0` means the last session with the ACS
succeeded. The ACS now lists the router as a new device: its first Inform carries the
`0 BOOTSTRAP` event.

:::note
Use plain HTTP only to test a setup in a private network. Anyone on the path can read and change
the parameters of an HTTP session. In production, use HTTPS and keep `check-certificate=yes`.
:::

## Check and troubleshoot

`status` shows whether the client is configured: `disabled`, `waiting-url` (enabled, but no ACS
URL) or `running`. A failing ACS does not change it. Failures show in `last-session-error` and
`retry-count`. For example, with a password the ACS does not accept:

```routeros
/tr069-client/print
```

```text
                      enabled: yes
                      acs-url: https://acs.example.com:7547/
                     username: cpe-0001
      periodic-inform-enabled: yes
     periodic-inform-interval: 1d
  connection-request-username: acs
      connection-request-port: 7547
            provisioning-code:
           client-certificate: none
            check-certificate: yes
                       status: running
           last-session-error: HTTP authentication error. Wrong username/password.
                  retry-count: 3
```

The client retries a failed session with a growing delay, from a few seconds up to minutes, and
resets `retry-count` after the next successful session. A corrected setting is used at the next
retry.

To follow each session, log the `tr069` topic:

```routeros
/system/logging/add topics=tr069
/log/print where topics~"tr069"
```

```text
 2026-11-23 08:16:36 tr069,debug starting session, events: [4 VALUE CHANGE, 1 BOOT, ]
 2026-11-23 08:16:36 tr069,debug session finished with error: "Network unreachable"
 2026-11-23 08:16:36 tr069,debug scheduled next Session retry after 7 seconds
 2026-11-23 08:16:43 tr069,debug starting session, events: [4 VALUE CHANGE, 1 BOOT, ] retry-count: 1
 2026-11-23 08:16:43 tr069,debug send: Inform
 2026-11-23 08:16:43 tr069,debug session finished with error: "HTTP authentication error. Wrong username/password."
 2026-11-23 08:16:44 tr069,debug scheduled next Session retry after 18 seconds
 2026-11-23 08:17:02 tr069,debug starting session, events: [4 VALUE CHANGE, 1 BOOT, ] retry-count: 2
 2026-11-23 08:17:02 tr069,debug send: Inform
 2026-11-23 08:17:02 tr069,debug session finished with error: "HTTP authentication error. Wrong username/password."
 2026-11-23 08:17:02 tr069,debug scheduled next Session retry after 31 seconds
```

Here the first session after a reboot started before the DHCP client had an address, and the
following ones were refused by the ACS. A successful session ends with `session finished ok` and
`scheduled next Periodic Inform`.

Common errors in `last-session-error`:

| Error | Cause |
| :-- | :-- |
| `HTTP authentication error. Wrong username/password.` | The ACS refused `username` and `password`. |
| `SSL: ssl: no trusted CA certificate found (6)` | The CA that signed the ACS certificate is not in the certificate store. |
| `SSL: ssl: name verification failed for: "CN=..." (6)` | The ACS certificate is for another name than the host in `acs-url`. |
| `resolving error` | The router cannot resolve the host name in `acs-url`. Check `/ip/dns`. |
| `Connection refused` | Nothing listens on the host and port in `acs-url`. |
| `Network unreachable` | The router has no route to the ACS yet, for example right after boot. |
| `HTTP error code: 500` | The ACS answered with an HTTP error. Check the ACS logs. |

If the ACS cannot reach the router with a connection request, check the firewall rule from the
example and its counters, and the connection request credentials on the ACS.

## How a session works

The router starts every session. It sends an Inform RPC that lists the events that caused the
session, the device identity and a few parameters. When the router has nothing more to send, the
ACS calls its RPCs: reading and setting parameters, downloads, uploads, reboot or factory reset.

| Event in the Inform | When |
| :-- | :-- |
| `0 BOOTSTRAP` | First session with an ACS: after the client is enabled for the first time, after `acs-url` changes, and after a configuration reset. |
| `1 BOOT` | After a reboot, and when the client is enabled. |
| `2 PERIODIC` | Every `periodic-inform-interval` (default one day), if `periodic-inform-enabled=yes`. |
| `4 VALUE CHANGE` | A client setting changed since the last session. |
| `6 CONNECTION REQUEST` | After a connection request from the ACS. |
| `7 TRANSFER COMPLETE` with `M Download` or `M Upload` | After a download or upload the ACS asked for, with the result. |
| `M Reboot` | After a reboot the ACS asked for. |

The Inform identifies the router with Manufacturer `MikroTik`, an OUI, a ProductClass and a
SerialNumber. It also carries the RouterOS version
(`Device.DeviceInfo.SoftwareVersion`), `provisioning-code` (`Device.DeviceInfo.ProvisioningCode`)
and the connection request URL (`Device.ManagementServer.ConnectionRequestURL`).

A connection request is an HTTP request from the ACS to that URL,
`http://<router address>:<connection-request-port>/<random path>`, where the address is the
router's own address. The ACS must be able to open a TCP connection to it, so a router behind NAT
receives connection requests only if the NAT device forwards the port. The router accepts the
request only with HTTP Digest authentication and the `connection-request-username` and
`connection-request-password`. It then starts a new session with the configured ACS. A connection
request cannot make the router contact any other server.

## Parameters and data models

Parameters are name and value pairs, such as `Device.DeviceInfo.SoftwareVersion`. The set of
parameters a device supports is its data model. The BBF defines the root data models TR-098 and
TR-181 (Issue 1 and Issue 2), on which vendors base their parameters. The RouterOS data model is
based on TR-181 Issue 2: the router reports `Device.RootDataModelVersion` 2.15. MikroTik-specific
parameters start with `X_MIKROTIK_`, for example `Device.DeviceInfo.X_MIKROTIK_SystemIdentity`.

Some parameters map to RouterOS settings. For example, setting
`Device.DeviceInfo.X_MIKROTIK_SystemIdentity` changes `/system/identity`, and setting
`Device.ManagementServer.PeriodicInformInterval` to `300` sets `periodic-inform-interval=5m`.

See the [RouterOS TR-069 parameter reference](pathname:///assets/tr069_parameters.html) for all
supported parameters.

## Change the configuration

Not every RouterOS setting has a CWMP parameter. To change any setting, the ACS sends a RouterOS
script with the Download RPC and FileType `3 Vendor Configuration File`. The URL's file name decides
what the router does with it. Put the file on an HTTP or HTTPS server that the router can reach,
for example the file server of the ACS:

- A file name ending in `.alter` changes the configuration: the router runs the script as it is,
  without a reboot, and reports the result with TransferComplete.
- Any other file name replaces the configuration: the router removes the whole configuration,
  reboots and applies the file. The next session starts with `0 BOOTSTRAP` and `1 BOOT`.

For example, a file named `identity-dns.alter` with this content renames the router and sets its
DNS server:

```routeros
/system/identity/set name=CPE-altered
/ip/dns/set servers=192.0.2.53
```

:::warning
A file that replaces the configuration must bring the router back to the ACS on its own. The rest
of the file is not applied after a line that fails, so a single error can leave the router without
the TR-069 client and out of reach of the ACS. Test each file on a local router first. Things to
include:

- A [startup delay](../getting-started/configuration-management/#startup-delay), so that
  the interfaces exist before the script configures them.
- Passwords: an exported configuration, including the file the router sends with the Upload RPC,
  does not contain them, including the TR-069 client password. Such a file cannot replace the
  configuration unchanged.
- [Certificates](../authentication-authorization-accounting/certificates) that the
  configuration needs, such as the CA certificate of the ACS.

:::

## Upgrade RouterOS

The CWMP standard upgrades firmware with the Download RPC, FileType `1 Firmware Upgrade Image` and
a single URL (HTTP or HTTPS). RouterOS is installed as packages, so the URL points to an XML file
that lists the package files to install, for an upgrade or a downgrade. The router downloads the
XML, checks it, downloads every listed file and installs them as in an upgrade by package file
upload, then reboots. It reports the result with TransferComplete in the first session after the
reboot (events `7 TRANSFER COMPLETE`, `M Download` and `1 BOOT`).

Put the XML file and the packages on an HTTP or HTTPS server that the router can reach, and send the
Download RPC with the URL of the XML file, for example `https://example.com/path/upgrade.xml`. List
the `tr069-client` package together with the RouterOS package, so that the client is upgraded with
it. The packages must match the router's architecture, which the router reports in
`Device.DeviceInfo.X_MIKROTIK_ArchName`:

```xml
<upgrade version="1" type="links">
   <config/>
   <links>
       <link>
          <url>https://example.com/routeros-X.Y.Z-mipsbe.npk</url>
       </link>
       <link>
          <url>https://example.com/tr069-client-X.Y.Z-mipsbe.npk</url>
       </link>
   </links>
</upgrade>
```

If the download fails, the router reports a fault in TransferComplete, for example `9015` with
`Connection refused`.

:::note
Upgrade step by step: first upgrade a router you have tested locally, and check that it reconnects
to the ACS and that the functions you need work. Then upgrade groups of routers. Do not upgrade all
remote routers at once. Serve the files over HTTPS in production.
:::

## Upload files to the ACS

With the Upload RPC, the router sends a file to the URL the ACS gives, with HTTP PUT, and reports the
result with TransferComplete. The FileType selects the file:

- `1 Vendor Configuration File`: the current configuration, as `/export` shows it. Passwords and
  other sensitive values are not included.
- `2 Vendor Log File`: the log, similar to [`/log/print`](../cli-reference/log): one line per
  entry with the time (in ISO 8601 format), topics and message.
- `X MIKROTIK Factory Configuration File`: the default configuration script that runs at the next
  configuration reset. If a custom script is installed, this is the custom script, which differs
  from the one `/system/default-configuration/print` shows.

## Reset the router to its default configuration

The FactoryReset RPC resets the configuration in the same way as this command:

```routeros
/system/reset-configuration skip-backup=yes
```

The reset removes the whole configuration, including certificates, and runs the default
configuration script. The default configuration differs between devices (see [Default
configurations](../getting-started/configuration-management/default-configurations)). To bring
routers back to the ACS after a reset, install a custom default configuration that configures the
TR-069 client, as the next section describes.

## Prepare routers for TR-069 management

A provider who manages routers over TR-069 can replace MikroTik's default configuration with a
custom script that brings the router back to the ACS after a reset: a FactoryReset RPC,
`/system/reset-configuration` or the reset button. This makes a router reachable again after a
configuration that cannot be fixed remotely.

The custom default configuration script can be installed in two ways:

- With Netinstall, which installs the script in place of MikroTik's default configuration.
- With the Download RPC and FileType `X MIKROTIK Factory Configuration File`. The router stores the
  script without a reboot and without changing the current configuration.

After a Download of the script, `/system/default-configuration/print` keeps showing MikroTik's
script. The custom script shows in
`/system/default-configuration/custom-script/print`, and `/export` starts with the comment
`# custom default configuration script installed`.

:::warning
The script runs on a router with an empty configuration and no certificates. If it fails, the
router can end up unreachable for the ACS. Test it with a reset on a local router first.
:::

At minimum, the script imports the CA certificate of the ACS, configures IP connectivity, a
firewall and the TR-069 client. The ACS configures the rest.

This script assumes that ether1 is the WAN port, that the router gets its address from a DHCP
client, and that the ACS at 198.51.100.10 uses a certificate signed by the CA in the script. The
certificate in the script is a placeholder: replace it with your CA certificate, and replace the
address, `acs-url` and the credentials. Add your own configuration.
